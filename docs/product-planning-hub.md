## 1. 产品总监结论

PrivateCloudDrive 当前已经不是“缺一个大功能”的阶段，而是进入了“功能已经较多，但需要统一规划、发布收口、设计收敛和长期可维护”的阶段。

当前最核心瓶颈：

> 项目已经从工程实现进入产品化阶段，但规划系统、设计决策系统、发布验收系统还没有成为唯一中枢。

所以下一步不应该继续无序扩功能，而应该进入：

> V1.2 RC / Productization Sprint：把已实现的文件管理、媒体库、相册、分享、OSS、MAUI UI 等能力收口为可发布、可部署、可验收、可长期使用的版本。

## 3. 当前产品定位

推荐定位：

> PrivateCloudDrive 是面向个人、家庭和小团队的私有部署移动优先云盘与轻量媒体库，重点解决“我如何安全、低心智、长期地管理自己的文件、照片和视频”。

一句话：

> 把自己的服务器、NAS、迷你主机或云主机，变成一个手机可稳定访问的私有文件与媒体中心。

---

## 4. 当前明确不做

短期不要做这些方向，除非 V1.2 RC 与 V1.3 运维规划版完成：

| 不做方向 | 原因 |
|---|---|
| NAS OS / RAID / 磁盘池 | 会把产品拖向操作系统级复杂度 |
| SMB/NFS/AFP 协议 | 不是当前移动优先云盘主线 |
| 企业网盘/审批流/复杂组织架构 | 当前定位是个人/家庭/小团队，不是企业协同平台 |
| Office 在线协作 | 技术复杂度高，偏离文件与媒体中心主线 |
| AI 相册/AI 搜索 | 可作为 V2 候选，不能早于稳定发布与备份恢复 |
| 桌面同步客户端 | 数据一致性成本高，应在灾备和权限模型后再做 |
| 下载器平台 | 会改变产品心智，不适合当前阶段 |
| 炫技型 UI / 过度手绘主界面 | 核心 App 是工具产品，应长期稳定、信息清晰 |

## 5. 设计决策基线

### 5.1 App 主设计方向

PrivateCloudDrive 的核心 App UI 应遵循：

- 工具优先。
- 信息清晰。
- 状态明确。
- 私有部署透明。
- 稳定、安静、长期使用。
- 文件名、大小、时间、状态、容量、服务器地址等信息优先。
- 不使用过强营销感、不使用过多装饰背景、不牺牲列表效率。

主设计文档优先级：

1. `docs/product-planning-hub.md`：最高产品决策入口。
2. `docs/open-source.md`：开源发布、许可证、维护政策与公开仓库文档完整性要求。
3. `docs/roadmap-public.md`：对外公开的公司产品方向、版本路线和贡献优先级。
4. `docs/market-feasibility-meeting-2026-05-17.md`：市场可行性、是否继续开发、产品偏差诊断与“手机优先私有备份网盘”转向结论。
5. `docs/team-operating-model-private-backup.md`：团队优化、11 人常驻核心小队、顾问池、冻结岗位和 2 周 Sprint 作战模型。
6. `docs/product-feature-map.md`：长期功能地图、版本边界与 Now/Next/Later 分层依据。
7. `docs/open-design-ui-redesign.md`：经用户指定的 Open Design / Claude Design 新 UI 方向与页面规范。
8. `docs/prototypes/open-design-mobile-prototype.html`：Open Design 高保真移动端原型，用于视觉对齐与实现验收。
9. `docs/product-ui-baseline.md`：历史/保守 UI 基线；若与 Open Design 冲突，以 Open Design 文档为准。
10. `docs/ui-design.md`：具体 UI 规范与页面设计；需要逐步按 Open Design 更新。
11. `docs/plans/*.md`：单页面或单任务设计计划。
12. `docs/design-explorations/*`：探索稿，不直接作为开发依据。

### 5.2 Doodle / 手绘风格处理原则

如果 `Design.md` 或资源体现 Doodle/手绘/强插画风格：

- 不作为核心 App 主界面风格。
- 可用于品牌探索、官网、空状态插画、营销素材。
- 进入 App 前必须经过设计评审，不能影响文件管理效率与状态可读性。

## 7. 需求进入开发的判断标准

任何新需求进入开发前，必须回答下面问题：

| 问题 | 必须回答 |
|---|---|
| 解决谁的问题？ | 个人用户、家庭用户、小团队用户、部署管理员、开发维护者 |
| 解决哪个场景？ | 文件管理、媒体浏览、分享、安全、部署、备份、排障、设置 |
| 当前痛点是什么？ | 不能只写“优化体验”，必须有具体痛点 |
| 优先级是什么？ | P0/P1/P2/探索 |
| 是否符合当前版本目标？ | V1.2 RC 只做收口，V1.3 做运维规划 |
| 不做什么？ | 明确边界，防止范围膨胀 |
| 涉及哪些页面/API/数据？ | 必须列出影响面 |
| 如何验收？ | 命令、真机步骤、测试项、文档项 |
| 是否影响数据安全？ | 文件、Blob、DB、分享、权限、token |
| 是否影响部署？ | Docker、PUBLIC_URL、存储、OSS、环境变量 |

如果这些问题回答不清楚，不进入开发。

## 8. 设计稿进入开发的判断标准

任何 UI/设计稿进入开发前，必须满足：

1. 绑定一个真实用户任务，而不是只描述风格。
2. 明确当前页面的问题。
3. 明确新的信息架构。
4. 明确视觉基线是否符合工具型产品。
5. 明确涉及的组件、文案、状态、错误提示。
6. 明确 API 和数据依赖。
7. 明确空状态、加载态、错误态、弱网态。
8. 明确验收标准。
9. 明确是否进入 V1.2 RC、V1.3 或探索池。
